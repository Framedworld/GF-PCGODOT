# WP13-P1: node and data-layer performance

Status: implemented on the P1 worktree branch, one commit per optimization. Everything is pure GDScript. No native code, node API, settings or saved-data format changed. The golden suite, the seed-zero suite and the whole test suite pass unchanged. Every optimization was also checked for byte-identical output with an exact fingerprint (see "How output identity was checked"). Full suite: 2494 cases (2456 before plus 38 new), 0 failures, 0 skipped, 1 orphan, exit 101. This is the same pre-existing orphan in `surface_sampler_test.gd` as the baseline.

## Summary

- **New tools** in `demo/tests/perf/`. Both are scripts, not tests.
  - `node_benchmark.gd` times 25 node cases, 12 data-layer primitives and the four executor phases at 1k, 10k and 100k points. It can also print an exact output hash per case.
  - `exact_fingerprint.gd` prints, for every golden graph and node, a SHA-256 of the raw output bytes plus every logged message. The golden suite rounds floats to 1/1000, so it cannot catch a last-bit change.
- **14 optimizations** are kept: `expression`, `attribute_filter_range`/`density_filter`/`point_filter_range`, `filter`, `transform`/`transform_points`, `difference`, `sample_points`, `point_offsets`, `partition`, `grid`/`surface_sampler`/`sample_mesh` (through a new `FlowData.point_seed_stream`), and in `flow_data.gd`: `Data.filter`, `Data.duplicate`, `TransformsStream`, `getEffectiveBounds` and `findStream`.
- **Typical speedups** at 1k to 100k points:
  - `expression`: 4 to 7×
  - `attribute_filter_range` and `density_filter`: about 4×
  - `point_offsets`: about 4×
  - `filter`: about 3×
  - `sample_points`: about 3×
  - `difference` (A minus B): about 2×
  - `transform` and `transform_points`: about 1.6 to 2×
  - `TransformsStream.atIndex`: about 1.6× (2.5× with `rotation_quat`); it is the per-instance path of the spawners
  - `getEffectiveBounds`: 2×
  - `grid`: 1.3 to 1.4×
- **The WP1 47-node graph** (50 points; `executor_benchmark.gd` scenario A, sequential) went from about 12.7 ms to about 9.4 ms per evaluation. Two interleaved runs each: 12.55 and 12.94 ms before, 9.49 and 9.25 ms after. The subgraph scenario B went from 50.6–55.9 ms to 37.6–38.7 ms. The node bodies inside it went from 8.4 to 5.8 ms; the executor's own build and finalize phases barely moved (see "Rejected and not attempted").
- **Every optimization has a parity suite.** Most run the pre-change node script, kept verbatim under `demo/tests/nodes/support/*_reference.gd`, side by side with the new one. They compare output bytes and every logged message, including script errors on malformed input.
- **Rejected ideas** are listed with their measurements:
  - an Expression parse cache
  - direct Euler-to-matrix math
  - duplicating a settings prototype
  - the `registerStream` selector shortcut
  - rewriting the `eulerToBasis` body

## Method

- **Machine.** The shared 4-core build container, Godot 4.6 headless, with the Linux debug native library loaded. Other agents were using the machine, so single runs vary by 10–50%.
- **Before and after.** Two exported trees were measured in alternating runs:
  - "Before" is a `git archive` export of the base commit `d5bd9b6`, or of the previous commit when one optimization was measured in isolation.
  - "After" is the work tree.

  Each figure is the median of the per-run medians, with the min–max range across rounds. Each run times every case 15 times at 1k, 7 at 10k and 3 at 100k, or more with `FLOW_NB_SCALE`.
- **Element runs.** Node cases run the element the way the executor does: a fresh element, fake source elements holding the inputs, `preExecute`, then `run`.
- **Inputs.** Seeded random points with non-zero Euler rotations, sizes from 0.5 to 2, density, seed, two float attributes and an int `group` with 10 values.
- **Profiling.** The engine profiler is not usable headless, so sections were timed with `Time.get_ticks_usec()` in scratch scripts. Each per-optimization section below names what was timed.

## Optimizations (in commit order)

Each entry gives the cost found and the change. The numbers come from interleaved runs of the previous commit against the change alone, ms before → after. Every entry was checked with `exact_fingerprint.gd` over the 56 golden graphs and with the benchmark's fingerprint mode at 7, 1k and 10k points; no hash changed.

1. **`attribute_filter_range` (also `density_filter`, `point_filter_range`).**
   - **Cost found:** the numeric mode called `_stream_value_as_float` per point, which allocates a two-element Array, plus `_passes_range`, which reads three settings through the subclass chain.
   - **Change:** the values are converted once per stream type into a `PackedFloat64Array` with the same coercions (`float()`, `length()`, the RGB mean, 0/1). The range test reads the settings once. String streams keep the per-point converter.
   - **Measured:** `density_filter` 2.65 → 0.80 (1k), 24.3 → 6.2 (10k), 240 → 62 (100k). `attribute_filter_range` on a Vector stream: 3.19 → 0.83, 29.3 → 6.5, 309 → 63.
   - **Test:** `tests/nodes/attribute_filter_range_typed_loop_test.gd` compares against the original per-point logic for every type, broadcast stream, flag combination, boundary value, NaN and bad string.
2. **`expression`.**
   - **Cost found:** a scratch profile at 100k points with 8 streams, per point:
     - copying all 8 stream values into the input array through a nested loop over an untyped Array: 1.44 µs;
     - `FlowData.Data.writeValue`: 1.2 µs;
     - `Expression.execute`: 0.2–0.3 µs.
   - **Change:**
     - Only streams whose name occurs in the expression text are bound, keeping their order, so duplicate names resolve as before.
     - Up to four streams are copied with unrolled locals.
     - The first point goes through `evaluateAndSaveResult`, which creates the container. Later results whose type matches the container are stored with an indexed write; anything else still goes through `writeValue`.
     - Tracing, and inputs with a stream shorter than the point count, keep the original loop inline, so they fail exactly as before.
   - **Measured:** 3.0 → 0.61 (1k), 47.7 → 5.1 (10k), 324 → 50 (100k) for `density * 0.5 + 0.25`. The other four expressions moved similarly.
   - **Test:** `expression_fast_path_test.gd` runs the old script, kept verbatim in `support/expression_reference.gd`, side by side. It covers 30 expressions: scalar, vector, Vector2, Vector4, Quaternion and string results, mixed result types, coercion into existing streams, arguments, `$` selectors, five or more streams, `expose_arrays`, short and empty streams, one point, and tracing. It compares output bytes and every logged message.
3. **`Data.filter` and `Data.size()`.**
   - **Cost found:** `registerStream` costs about 5 µs per call, `filteredStream` recomputed `size()` per stream, and `size()` built `keys()`.
   - **Change:** a gathered container always matches its type, so for a plain name of the right canonical type and length the registration is exactly a dictionary insert (same keys and order). `filter` now does that. Broadcast streams, failed gathers, selector-like names, canonical type errors and length mismatches still go through `registerStream`. `size()` iterates instead of building `keys()`.
   - **Measured:** `Data.filter` 0.074 → 0.050 (50 points), 0.233 → 0.206 (1k). At 10k and above it is within noise, because the per-element gather is unchanged. At 50 points `partition` went 0.93 → 0.67 and `filter` 0.32 → 0.24.
   - **Test:** `tests/attributes/data_filter_fast_path_test.gd` checks every type and malformed streams (StringName names, `Yaw`, `$Density`, `a.b`, `@data.x`, wrong canonical type, bad type, short and long streams, empty name) against `filteredStream` + `registerStream`.
4. **`filter`.**
   - **Cost found:** one `_passes_numeric_condition` call per point with Variant arguments, about 1.5 µs.
   - **Change:** Float, Int (32-bit), Bool and Double convert to doubles exactly, so the comparison runs on two `PackedFloat64Array`s with one typed loop per condition. Int64 (which can exceed 2^53), mismatched containers and short containers keep the original loop.
   - **Measured:** 2.0 → 0.83 (1k), 19.2 → 9.7 (10k), 323 → 118 (100k, noisy).
   - **Test:** `filter_typed_loop_test.gd` compares against the old script for all 10 conditions × 8×8 type pairs, constants, `true`/`false`, broadcast B, NaN, ±inf, Int64 above 2^53, out-of-range condition values and malformed streams.
5. **`TransformsStream` (`basisAt`, `atIndex`, the `rotation_quat` Euler derivation).**
   - **Cost found:** two or three nested static calls per point.
   - **Change:** the bodies of `eulerToBasis`, `quatToBasis(vec4ToQuat())` and `quatToEuler` are inlined. These are the same engine calls on the same values; 200,000 random Euler angles gave 0 bit differences.
   - **Measured:** `atIndex` over all points 1.06 → 0.58, 11.0 → 5.9, 100 → 71. With `rotation_quat`: 2.23 → 0.76, 20.1 → 11.8, 202 → 95. `copy`: 1.11 → 0.90, 9.8 → 7.5, 110 → 74.
   - **Test:** `transforms_stream_inline_test.gd` compares bit for bit against the public helpers, including the derived Euler stream.
6. **`transform` / `transform_points`.**
   - **Change:** `max - min` ranges are computed once. `resolve_seed`, `point_seed`, `eulerToBasis` and `basisToEuler` are inlined with the same expressions.
   - **Measured:** 2.07 → 1.31 and 2.88 → 1.61 (1k); 18.3 → 11.4 and 28.5 → 13.9 (10k); 195 → 110 and 288 → 191 (100k).
   - **Test:** `transform_inline_test.gd` compares against the old script for every seed source (per point, broadcast, position hash, wrong length), both rotation spaces, both scale modes, a graph seed and missing streams.
7. **`difference`.**
   - **Cost found:** at 100k points:
     - building both R-trees: 188 ms;
     - four native overlap queries: 89 + 89 + 130 + 169 ms;
     - sanitizing all four lists with a Dictionary and a sort: 62 ms.

     Point-set A minus B reads one of the four lists.
   - **Change:**
     - Only the lists the operation reads are queried, and only the trees they need are built. The queries are `const` and pure.
     - Results that are already strictly increasing and in range, which is what `GDRTree` returns, skip the sanitizing pass.
     - `_safe_sizes` uses a typed local.
   - **Measured:** 5.06 → 2.03, 43.6 → 22.3, 809 → 382.
   - **Test:** `difference_lazy_lists_test.gd` compares against the old script for 5 operations × 4 density functions × 4 overlap sources × keep flag, with and without bounds and steepness streams, plus empty and degenerate inputs.
8. **`sample_points`.**
   - **Cost found:** three calls per sample (a Callable, then two methods) for a 2D sequence that depends only on the sample number and the phase, plus `effective_seed()` and `point_seed` per output point.
   - **Change:** the 2D sequence is computed once per run. The 3D one still draws from the RNG per sample, in the same order. The node seed is hoisted out of the loop.
   - **Measured:** 5.01 → 1.83, 46.8 → 21.0, 511 → 178.
   - **Test:** `sample_points_precomputed_test.gd` covers all four distributions, phase, group layouts including degenerate ones, inherited attributes, graph seed, bounds input and empty input.
9. **`point_offsets`.**
   - **Cost found:** up to ten settings reads, three `_setting_vec` calls and a per-offset `eulerToBasis` per output point. The stream copy re-read the source and called `bcast_idx` per copy.
   - **Change:** per-offset values (offset, rotation and its basis, size, label) are resolved once, and settings are read once. The Euler helpers are inlined, and each anchor value is read once per stream.
   - **Measured:** 7.79 → 2.16, 52.7 → 16.4, 568 → 144.
   - **Test:** `point_offsets_hoisted_test.gd` covers all 32 flag combinations × short lists × Euler and quaternion anchors, plus malformed streams, no rotation and no offsets.
10. **`FlowData.point_seed_stream`** (new data helper, used by `grid`, `surface_sampler`, `sample_points`, `sample_mesh` and `FlowSpatial.make_points_data`).
    - **Cost found:** `point_seed` costs about 770 ns per call, of which allocating a four-element Array to hash is most.
    - **Change:** the helper reuses one key array. The hash of an Array depends only on its elements, so the values are identical. About 450 ns per point. Negative counts keep the original loop and its resize errors.
    - **Measured:** `grid` 1.13 → 0.75, 9.97 → 7.70, 99.9 → 65.5. `surface_sampler` 1.71 → 1.45, 16.3 → 12.5, 162 → 139.
    - **Test:** `point_seed_stream_test.gd` checks the helper element by element against `point_seed` over 3,006 positions × 6 seeds, including NaN and ±inf. It also compares `grid` and `surface_sampler` with their old scripts, including negative counts.
11. **`partition`.**
    - **Change:** Int, Int64, Bool and String values have exactly one `"%s"` form each, so they are grouped by value, giving the same groups in the same first-seen order. Floats, vectors and tracing keep string keys.
    - **Measured:** 2.00 → 1.39, 16.9 → 8.5, 128 → 75.
    - **Test:** `partition_exact_keys_test.gd` covers every attribute type, including floats whose string forms collide (0.1 and 0.10000001), the id stream, tiny inputs and tracing.
12. **`Data.duplicate`.**
    - **Change:** one lookup per stream instead of five, with the same copy semantics.
    - **Measured:** 10–27% across sizes, for example 0.017 → 0.015 ms at 50 points.
    - **Test:** `data_duplicate_lookup_test.gd` compares with the previous definition and checks that the copy is independent of the source.
13. **`findStream`.**
    - **Change:** `translateStreamName` and `split(".")` are skipped for names they return unchanged; only `@last`, Yaw/Pitch/Roll and `$` selectors are translated.
    - **Measured:** 1.6 → 1.4 µs per plain lookup (−12% and −14% in two runs).
    - **Test:** `data_selector_translation_test.gd` keeps the previous `findStream` and `registerStream` bodies and compares 31 selector forms. That covers 620 `registerStream` combinations, with results, Data bytes and logged messages.
14. **`getEffectiveBounds`.**
    - **Change:** `bcast_idx` and `size()` are no longer called per point.
    - **Measured:** 0.275 → 0.118, 2.75 → 1.30, 36.8 → 13.5.
    - **Test:** `effective_bounds_inline_test.gd` compares 375 combinations of per-point, broadcast, missing and malformed bounds and size streams with the previous body.

Thread safety: no new statics. `point_seed_stream` and all hoisted state are locals, so the WP1 rules and the traits table are unaffected.

| Cache parsed `Expression` objects per (text, input names) with a Mutex | `Expression.new()` + `parse` costs 2.6–3.6 µs, about 2% of an `expression` node run at 50 points (110–140 µs) and under 0.5% at 1k. `Expression.execute` writes error state into the object, so a shared instance is not thread-safe; a cache would need a per-thread pool. | Rejected: under 10%, and it adds a pool. |
| Direct Euler-to-matrix math instead of `Basis.from_euler` | `Basis.from_euler` computes in float32 with `sinf`/`cosf`. GDScript math is double precision. On 200,000 random angles, 199,787 bases differed (1,149,523 of 1,800,000 elements) in the last bits. | Rejected: not bit-identical. Inlining the `from_euler` call at the call sites gave the speedup instead (items 5, 6, 9). |
| Rewrite the `eulerToBasis` / `basisToEuler` bodies (one constructor instead of three assignments) | 440–470 ns → 440–570 ns per call; no measurable gain, because the call itself dominates. | Rejected. |
| Build run settings by `settings_prototype.duplicate()` instead of replaying assignments | 40–45 µs against 7.5–8.2 µs per settings object (5×). `duplicate` sets every stored property and fires every setter. | Rejected. |
| Skip `translateStreamName` and `split` in `registerStream` (as in `findStream`) | In isolation the skipped part fell from 0.84–1.29 µs to 0.40–0.70 µs, but the whole call improved only −2% to −5% in interleaved runs (4.3 → 4.1 µs). | Rejected: under 10%. The parity test still pins `registerStream`. |
| Cheaper element construction | `FlowNodeBase.new()` alone costs 5.5–6 µs of the 9–15 µs per element. That is GDScript member initialization (about 40 members, typed arrays, an RNG at 0.6 µs). | Not attempted: removing or lazily creating members changes the element API. |
| Cheaper finalize | Of about 1.1 ms, 1.04 ms is releasing the 47 elements and their Data; publishing variables and params takes 22 µs. | Not attempted: inherent to fresh elements per run. Pooling elements would contradict the WP1 design. |
| `readAllInputsForBulk` in a single pass over the connections | 12 µs per element, about 0.6 ms (6%) of the 47-node evaluation. `execute_node` already wires the same inputs. | Not attempted; a candidate for an executor package. The whole executor overhead now outside the node bodies is about 30 µs per element. |
| `FlowCompiledGraph.for_graph` validation | Hashes `graph.data` on every lookup: 0.16–0.19 ms per evaluation (about 2%). | Not attempted: the hash is what detects in-place edits of the graph data. |
| `difference`: derive the overlap list as the complement of the no-overlap list | It would save one native query per tree for Union. Correctness depends on GDRTree internals (`createResult` iterates `[0, size)`). | Not attempted: lazy queries already halve the default operation. |
| `Data.filter` per-element gather | About 45 ns per element and stream at 100k (17.9 ms for 50k × 8 streams). Packed arrays have no gather primitive in GDScript; slices only help for contiguous runs, which filters rarely produce. | Native candidate (below). |
| `self_pruning`, `sort`, `merge`, `math_op` | Already typed loops or native (`GDRTree.self_prune`, `GDStreamUtils` sort). The remaining GDScript is `Data.filter`. | No change. |

## Which loops would benefit from native code

These are the per-element costs of the GDScript that remains, after the changes above. They are taken from the after column at 100k points; the native estimates come from what the same work costs in the engine's C++. Nothing here is implemented.

| Loop | GDScript cost now | What native would do | Estimated speedup |
|---|---|---|---|
| `Data.filter` / `_gatherStream` (used by every filter-type node, partition, sort, difference) | about 45 ns per element and stream; 18 ms for 50k points × 8 streams | typed indexed copy per packed type | 10–30× on the gather (memory-bound, 1–4 ns per element) |
| `FlowData.point_seed_stream` (generators) | about 450 ns per point | hash four ints with the engine's Array hash in C++; must call the same `Array::hash` so values are identical | 10–20× |
| `TransformsStream.atIndex` loops in the spawners (`spawn_meshes` per instance, `copy`) | about 600 ns per point (Euler); about 800 ns with `rotation_quat` | build `Transform3D`s, or the MultiMesh buffer directly, from position, rotation and size streams with `Basis::from_euler`, the same function GDScript calls | 15–30× for the transform build; more if the MultiMesh buffer is filled in one call |
| `transform` per-point RNG and basis | about 1.1 µs per point (seed, 7 `randf`, two bases) | the same `RandomPCG` seeding and `randf` as `RandomNumberGenerator`, plus `Basis::from_euler` | 20–40× |
| `expression` per point | 500–870 ns per point, of which `Expression::execute` is 200–300 ns | a native loop calling the same `Expression::execute` over the bound columns removes the GDScript loop and copies, not the interpretation | 2–3×; a compiled column evaluator would be 10×+ but is a semantics risk (Variant promotion rules) |
| `attribute_filter_range` / `filter` split | 150–250 ns per point (conversion, comparison, two appends), plus `Data.filter` | a typed compare that returns the inside and outside index arrays | 20–50× on the split; the overall node is then bound by the gather |
| `partition` grouping | about 300 ns per point (Dictionary per point) plus filters | group ids for int and string columns | 10× on grouping |
| `difference` / `self_pruning` broadphase preparation (`_safe_sizes`, `_broadphase_params`, finite checks) | about 300 ns per point | fold into the existing `GDRTree.add` / `overlaps` | 10–20× on that part; the R-tree work is already native |
| `getEffectiveBounds` | about 140 ns per point | broadcast-aware copy | 20–50× |

How to gate them so the committed Windows and macOS binaries stay valid:

- **Detection.** Put each function on an existing native class as a new static method (for example `GDStreamUtils.gather_f32`). Detect it with `ClassDB.class_exists("GDStreamUtils") and ClassDB.class_has_method("GDStreamUtils", "gather_f32")`, evaluated once and kept in a script constant or a static guarded like the other statics. `class_exists` alone is not enough: an older prebuilt binary has the class but not the method.
- **Fallback.** Keep today's GDScript as the fallback, behind one data-layer function per primitive (for example `FlowData.gather_stream(container, indices)`), so nodes call one entry point.
- **Parity test.** Write one settings-independent test per primitive that calls the native and the GDScript path directly on generated data and compares raw bytes:
  - inputs: random values, NaN, −0.0, ±inf, broadcast length-1, empty, out-of-range indices (the error path);
  - for seeds and transforms: values chosen to hit rounding at the 1/1000 quantization and at angle wrap-around.

  When the method is missing, the test is skipped with the reason recorded, as the golden suite already does for the native library. The golden suite and `exact_fingerprint.gd` then confirm identical graph output with each binary.
- **Ship together.** Because the binaries are prebuilt, a new method must ship in all three platform binaries in the same release, or the fallback silently runs on the stale ones (correct, just slower).

## How output identity was checked

- **`exact_fingerprint.gd`.** Uses the golden suite's discovery: 56 graphs and scene components, the same owners and inputs. It hashes, per node, the raw `var_to_bytes` of every container of every bulk and port, stream keys, names, types and order, `last_added_stream_name`, tags, kind, data attributes and the shape's `content_hash`. It also hashes every warning or error logged during each graph. The base output was recorded once; after every optimization the new output was diffed against it, ignoring only backtrace line numbers.
- **`FLOW_NB_FINGERPRINT=1 FLOW_NB_SIZES=7,1000,10000 node_benchmark.gd`.** Exact hash of every benchmark case, base against final: identical.
- **Parity suites.** Each optimization has one, listed above. Each was sanity-checked by mutating the new code (a wrong condition, a missing flag, a changed store) and seeing it fail.

## Pitfall found on the way

A test script that declares `class X extends FlowData.Data` (a subclass of the inner Data class) breaks GdUnit's discovery of the whole `tests` directory. The GDScript analyzer then rejects unrelated scripts with "Cannot use subscript operator on a base of type null" (`copy_attribute.gd:119`, `merge_attributes.gd:120`), and the run aborts with exit 105. The same suite passes when run alone, so only a full run shows it. Reference implementations in tests should be static functions that take the Data. Commit f53cc92 fixes the one suite that did this.

The machine is shared, so use three or more rounds and report the range.
