# WP13-R3: adversarial review of hierarchical and runtime generation

Reviewer R3. I did not write this code.

**Scope.** I reviewed these parts end to end:
- `world/*.gd`: `FlowWorld3D`, `FlowWorldGrid`, `FlowWorldCell`, `FlowCellRun` and `FlowGenerationSource`.
- The level analysis in `executor/flow_compiled_graph.gd`.
- `FlowGraphNode3D.generate_cell` and `begin_cell`.
- The nodes `grid_size`, `get_execution_bounds`, `cull_points_outside_bounds` and `grid_fill_bounds` (`world_anchored`).
- The hierarchical demo.

**Method.** For each failure hypothesis I first wrote a test (headless, deterministic, with the injected clock and source provider), and confirmed that it failed. I then made the smallest fix and committed it, one commit per bug. Tests that passed on their first run were kept only where they add coverage that did not exist before.

**Result.**
- 11 confirmed bugs, all fixed in `world/flow_world_3d.gd` and `world/flow_world_grid.gd`.
- 2 new test files, with 27 cases.
- No golden or seed-zero hash changed, and no existing test was edited.
- No change to the output of an existing graph, except as stated under bug 4: a forced regeneration after the world's settings changed now uses the new settings.

### 1. A cancelled cell was revived as Generated, but empty

When the scheduler cancels a cell's run, it puts the cell in CleaningUp. If the cell was wanted again before that cleanup ran, every revival path set it straight to Generated:
- the source coming back;
- `generate_cell`;
- `queue_bounds`;
- a finer cell needing it as a parent (`_parents_ready`).

The run had never finished, so the cell had:
- empty outputs;
- nothing captured for its finer cells, which then ran without the coarse data;
- no `cell_generated` signal;
- whatever partial content it had spawned.

`generate_cell` returned `{}` for such a cell.

**Fix.** `CellRecord.complete` records whether the cell's last run finished. `_revive` sends a cell whose run was cancelled back to Queued, and its component is reused.

### 2. A huge finite generation radius selected no cells

`_cells_near` converted `(p ± r) / level` to an int before clamping it to the world's range. With r = 1e30, or 1e19 at grid size 1, the conversion saturated to INT64_MIN and the following `- 1` wrapped. The window was then empty: the level got no cells at all, while `INF` worked.

**Fix.** The window is now clamped in floating point before the conversion.

### 3. No limit on the runtime cells around a source

A radius much larger than the world's cell count made one tick create a record for every cell in range, and then scan all of them for every cell it started.
- A 200 × 200 cell world queued 40 000 records in one tick.
- A 2e6 × 2e6 world at grid size 1 never finished.

**Fix.** The new constant `FlowWorld3D.MAX_RUNTIME_CELLS_PER_LEVEL = 16384` limits how many cells Runtime mode considers per level and per source.
- When a radius covers more, only the 127 × 127 window of cells nearest the source is used, clamped into the world.
- The first time this happens for a level, a warning names the constant.
- Manual and OnLoad requests are not capped, because they name their area explicitly.

### 4. A forced regeneration kept the old world settings

A component received the world's settings only when it was first acquired: `graph`, `seed`, `args`, `params`, `overrides`, `threaded` and `output_cache`. After changing `world.seed`, `generate_cell(..., true)` still ran with the old seed. The same applied to a cancelled cell queued again.

**Fix.** `_configure_component` applies the settings before every run.

**Output change (intended).** A forced regeneration after a settings change now gives the result for the new settings. Before, it gave the old ones. No baseline covers this.

### 5. `queue_bounds` after OnLoad went idle was never generated

In OnLoad mode the world turns processing off once it is idle. A later `queue_bounds` or `queue_all` queued cells that nothing ever ticked, although the method's documentation says that `tick()` generates them every frame in OnLoad and Runtime mode.

**Fix.** `queue_bounds` turns processing back on in those two modes, when the world is in the tree and outside the editor. Manual mode is unchanged: the caller ticks.

### 6. Grid sizes of 2^31 or more wrapped as int32 level ids

Grid sizes are kept in a `PackedInt32Array`. A `cell_size` of 3e9 snaps to 2^31; 1e12 and `INF` are also too large. Any of these wrapped on the way into the array:
- `levels()` read `[0]`, so the level was lost;
- `node_levels` still held the 64-bit size, so the marker's nodes were on a level the world never generated.

**Fix.** `FlowWorldGrid.snap_grid_size` clamps to `MAX_GRID_SIZE = 2^30`, and maps `INF` and `NaN` there too. Sizes up to 2^30 are unchanged.

`GridSizeNodeSettings._snap_to_power_of_two` is not clamped, so the deprecated `ctx.variables` annotation can differ above 2^30. Nothing reads that annotation.

### 7. Runtime mode kept the cells of a removed level forever

The runtime cleanup pass only walks the graph's current levels. After a graph edit that removes a grid size (for example a marker changed from 16 to 32), the cells of the old level were never visited again, and their content stayed wherever the source went.

**Fix.** Cells of a level that no longer exists are cancelled and cleaned up, except manual cells, which the runtime scheduler never cleans up (documented).

### 8. Unbounded queries with a coordinate other than (0, 0)

`generate_cell(0, c)` and `cleanup_cell(0, c)` normalise the coordinate to (0, 0), but these did not:
- `get_cell_state`;
- `get_cell_outputs`;
- `get_cell_errors`;
- `get_cell_component`.

After `generate_cell(0, Vector2i(5, -3))` returned outputs, `get_cell_state(0, Vector2i(5, -3))` returned NONE.

**Fix.** `_key` now normalises the coordinate, in one place.

### 9. A freed node from a source provider aborted every tick

`get_generation_sources` evaluated `entry is Vector3` before checking that an object entry was still valid. A custom `source_provider` that returned a freed node (for example a player reference kept in an array) raised "Left operand of 'is' is a previously freed instance" on every tick. The tick aborted, so nothing was generated or cleaned up any more.

**Fix.** Object entries are checked with `is_instance_valid` first.

### 10. One compiled-graph lookup per cell in each scheduler pass

`get_parent_cells()` goes through `FlowCompiledGraph.for_graph`, which hashes all of `graph.data` to validate the cached compilation. Two loops called it once per cell on every tick:
- the runtime cleanup pass, for every kept cell;
- `_fill_active`, for every queued cell, every time it started a cell.

| Case | Idle tick before | Idle tick after |
|---|---|---|
| Demo graph, 1325 cells | about 36 ms | about 20 ms |
| Padded test graph, 137 cells | 67 ms (about 237 lookups) | |

The frame budget is 4 ms. Settling the 1325 cells went from 32.7 s to 13.8 s (with a 1 s budget per tick).

**Fix.** Each pass looks the levels up once and passes them to a static `_parent_keys()`.

**Test.** The test is self-calibrating: it compares the idle tick with the cost of one lookup measured in the same run. It does not depend on absolute timing.

### 11. Switching to Runtime mode after `_ready` did nothing

Processing was enabled only in `_ready`, for the mode the world was loaded with. Setting `generation_mode = Runtime` later (after a loading screen, or from a menu) was a silent no-op.

**Fix.** A setter starts processing when the world switches to Runtime after it is ready.

## Suspected issues, not fixed

1. **Settings changed at run time leave stale coarse data.**
   - **What happens.** Generated cells are kept as they are (documented: a generated cell is returned as is unless forced). This applies after:
     - a graph edit that keeps the levels;
     - a change of `seed`, `params`, `overrides` or `world_bounds`.

     Their outputs and captured data still come from the old settings, and finer cells generated later use them.
   - **`world_bounds` shrinking.** Cells now outside the world are measured against a box of zero size at the clamped corner, so they can survive cleanup.
   - **Workaround.** Today you must call `cleanup_all()` after such a change. A per-record settings signature would fix it, but that is a design change, not a fix.
2. **Per-tick overhead outside the budget.** Even after fix 10, an idle runtime tick costs about 15 µs per known cell: about 20 ms for 1325 cells with the demo graph, against the 4 ms default budget. The cost comes from `_update_runtime_targets`, which makes one pass per level over every record, plus the radius query. Each cell started costs a full scan of the records in `_fill_active`. This is fine for the demo's 45 cells. It needs an incremental design (per-level indices, or recomputing only when a source crosses a cell), which is not a small fix.
3. **Pooled components keep user signal connections.** A handler a user connected to one cell's component (`generated`, `cleaned_up`) fires later for whatever cell reuses that component.
4. **Direct calls on a cell component conflict with the world.** If user code calls `generate()` or `cleanup()` on a cell component while the world is generating it, the world's run is cancelled behind its back. The next tick then sees a finished run and marks the cell Generated with empty outputs. Not tested; components are owned by the world.
5. **Float keys in `generation_radius` are ignored.** Keys such as `16.0` are not found, and the default radius is used silently. The documentation says int or String keys.
6. **A radius of −INF selects the whole world.** `_cells_near` treats any infinite radius as "everything". This needs absurd input, so it was not fixed.
7. **A FlowWorld3D that is not at the identity transform.** This is documented as unsupported: spawned content lands in the world's local space, while bounds and sources are global. There is no warning.
8. **Freeing the world without `cleanup_all()`.** The cell components are freed together with their own subtree. Content spawned outside the world (`spawn_parent_path`, target nodes) stays, exactly as for a freed `FlowGraphNode3D`.
9. **Extreme coordinates.**
   - `coord_of` and `get_cell_at` return a `Vector2i`, so they wrap when |p / size| > 2^31.
   - Ownership needs the cell size to be at least the float32 spacing at that coordinate. That was verified up to 1e7; with size 1 it fails beyond about 1.6e7, where cell edges cannot be represented.
10. **`grid_fill_bounds` `world_anchored` and `max_points`.** When a cell or the monolithic run reaches `max_points`, the results differ, so invariance only holds below the limit.
11. **`all_generated` after a cleanup-only period.** It is also emitted after a busy period in which cells were only cleaned up. This matches WP5.md ("emitted when the world goes from busy to idle"), but the signal name suggests otherwise.
12. **Cancelled runs emit `cell_cleaned_up` without `cell_generated`.** This is documented ("a generated (or generating) cell"). Listeners that pair the two signals must allow for it.

## Judged fine

- **Cell math.**
  - floor, not truncation, for negative coordinates;
  - points exactly on multiples of the cell size;
  - offsets up to 1e7;
  - integer `parent_coord`;
  - worlds smaller than a cell, and of zero height;
  - non-power-of-two sizes, which are snapped, and invalid levels, which are rejected with an error.
- **Level analysis.**
  - diamonds, including a marker on one branch;
  - several markers, and equal markers;
  - disabled markers (documented as markers);
  - a marker without input;
  - cycles (WP5 test);
  - variables across levels, where `get_variable` follows its `set_variable`;
  - markers inside loops and subgraphs, which are pass-throughs;
  - recompilation after a graph edit.
- **Preseeded data.**
  - Shared Data is not mutated by stock nodes in the fine cells.
  - Results do not depend on the order cells are generated in.
  - A fine cell requested before its parent exists generates the parent first.
- **Scheduler.**
  - zero or negative budget and concurrency;
  - re-entry from signal handlers;
  - freeing the world, reparenting it, and taking it out of the tree;
  - sources disabled, freed or teleported;
  - radius changes;
  - the pool bound and the reset of reused components;
  - `cleanup_all` while cells are generating.
- **Nodes.**
  - `cull_points_outside_bounds` on edges, with point bounds and with a margin (WP5 tests plus the conventions in `FlowWorldGrid`);
  - `get_execution_bounds` clipped to the world;
  - `grid_fill_bounds` `world_anchored` invariance on offset worlds.
- **Threaded and cached modes.** Results are identical to sequential (WP5 test). `Data.content_hash` includes the shape and the `@data` attributes, so cached cacheable nodes downstream of the execution bounds, such as `intersection`, see different keys per cell.

## Limits of this review

- Nothing was checked visually. The demo is covered only by its existing headless test.
- Real frame timing was measured with ad-hoc scripts (not committed), not profiled in a running game.
- Rotation was not covered: `world_bounds` is an AABB, and rotating the FlowWorld3D node is documented as unsupported. The "rotated world" hypothesis therefore reduces to item 7 above.
- Only the stock nodes listed above were used to check that preseeded inputs are not mutated. WP9's conformance harness covers the per-template rule.

## DEPRECATIONS rows (changed semantics)

| Node / API | Before | Now | Since |
|---|---|---|---|
| `FlowWorld3D.generate_cell(level, coord, true)` after changing the world's `seed`, `params`, `overrides`, `args`, `graph`, `threaded` or `output_cache` | Ran with the values of the cell's first generation | Runs with the world's current values (coarser cells are still not regenerated) | WP13-R3 |
| `FlowWorld3D` Runtime radius | Unbounded number of cells per source | At most `MAX_RUNTIME_CELLS_PER_LEVEL` (16384) per level per source, the nearest ones, with a warning | WP13-R3 |
| `grid_size` `cell_size` above 2^30 | Wrapped to an invalid level id | Clamped to 2^30 (`FlowWorldGrid.MAX_GRID_SIZE`) | WP13-R3 |
