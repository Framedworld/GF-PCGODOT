# WP13-R1: adversarial review of the executor and evaluator

Reviewer R1. Area: `executor/*.gd` (`FlowExecutor`, `FlowCompiledGraph`, `FlowNodeTraits`, `FlowOutputCache`, `FlowNodeWidget`), `flow_nodes_io.gd`, `node.gd`, `flow_node.gd` (`FlowGraphNode3D`) and the dock's evaluation path in `flow_editor.gd`.

Method: I read the area end to end and wrote down failure hypotheses. For each one I wrote a headless, deterministic test first. When the test failed, I made the smallest fix in its own commit. When it passed, I kept it only if it covers something no existing test covers.

All new tests are in `demo/tests/review/`:
- `r1_executor_review_test.gd` (10 cases)
- `r1_editor_review_test.gd` (8 cases)
- `r1_golden_purity_review_test.gd` (1 case)

Golden and seed-zero baselines did not change. No baseline hash changed.

## Tests kept as coverage (they passed)

- **`test_nested_subgraph_in_place_edit_reaches_the_parent`**: an in-place edit of a nested subgraph's `data` while the parent's compiled graph stays cached.
- **`test_nested_threaded_loops_keep_outputs_and_error_order`**:
  - Setup: three main-thread loops whose bodies have failing and succeeding pure branches, next to failing outer branches. Each loop iteration starts its own pool batch from the main thread.
  - Runs: 4 threaded runs, and 4 threaded runs with the output cache.
  - Result: outputs and the full `last_errors` order equal the sequential run.
- **`test_repeated_evaluations_do_not_grow_the_object_db`**: 200 evaluations each, in synchronous, threaded, cached and time-sliced mode, of a graph with a subgraph and variables. `Performance.OBJECT_COUNT` stays flat (2 or fewer).
- **`test_generate_reentrant_from_generated_signal`**: `generate()` called from a `generated` handler.
- **`test_public_runtime_api_signatures_are_unchanged`**: argument names and default counts of the public calls (WP1 requirement 9):
  - `evaluate_graph`, `begin_evaluation`, `evaluate_graph_snapshot`, `make_context`, `evaluate`;
  - `generate*`, `cleanup`, `is_generating`, `execute`;
  - the `GraphEvaluation` methods.
- **`test_partial_reevaluation_through_variables_reroutes_and_disable`**: a middle-node setting edit and a disable toggle reach consumers through `set_variable` → `get_variable` and a reroute. After each edit, the dock equals the runtime for the saved graph.
- **`r1_golden_purity_review_test`**: run settings share untyped Arrays and Dictionaries with `graph.data` (the compiled graph replays `dict_to_resource`'s assignments). Over every golden graph and scene, including nested graphs, I checked that sequential, threaded and cached regenerations never write into any graph's `data`. It takes about 30 s.

## Suspected or partly confirmed, not fixed

- **`expression` is not serialized in threaded mode.** `Expression.execute()` runs with `show_error` on, so a bad evaluation raises an engine error on a worker thread. I left it out of `LOGGING_TEMPLATES` because it is the most expensive pure node (2.6 of 7.4 ms in the WP1 benchmark). A fix that keeps the speed would pass `show_error = false` and report through `setError`. That is a node-script change, so it is the coordinator's call.
- **`print()` with `settings.trace` on**, in pure nodes (`merge`, `assets`, `expression`, `partition`, `math_op`, `copy`), also reaches Loggers from workers. It is a debug-only path; the scan ignores it.
- **The cache key holds Resources in settings by identity.** An in-place edit of a Curve or Gradient used by `curve_remap_density` or `remap` gives stale hits until `FlowOutputCache.clear()`. This is documented (WP1, `output_cache` tooltip), so I judged it as designed and did not change it. In input Data, an object-valued stream element is hashed by `resource_path` when it has one. That gives the same result, because the outputs reference the object and no cacheable node reads mesh or texture contents. If a resource were reloaded as a *different* object under the same path (`CACHE_MODE_IGNORE`), a hit would hand out the old object. I could not construct this through stock nodes.
- **`FlowOutputCache.max_entries < 0` hangs.** The eviction loop `while _entries.size() > max_entries` never ends. This is user error; a `maxi(max_entries, 0)` guard would fix it. I did not write a test, because the test itself would hang.
- **Settings property lists are cached per script and never cleared.** `FlowOutputCache._settings_props` and `FlowExecutor._resource_props` are cached by script id, and the compiled graph's replayed `assignments` are built once. After an editor hot reload that adds a settings property, the cache key and the replay miss that property until the graph data or registry changes. This is editor-only, because the cache is a runtime option.
- **Nested `evaluate_collecting_errors` in threaded mode.** A custom main-thread node that calls `FlowNodeIO.evaluate()` appends its nested errors directly to the outer synchronous log. All other elements' errors are buffered until the end of the threaded run, so the order of `last_errors` would differ from the sequential run. No stock node does this.
- **`cleanup()` during an async run** finishes the run first: its spawners run, then their content is deleted, and `generated` is never emitted for it. A script awaiting `generated` after `generate_async()` then `cleanup()` would wait forever. This existed before the round (`_finish_async_now(false)` since the runtime API round), so I left it alone.

## Judged fine

- **Compiled-graph invalidation.** The compiled graph tracks the `graph.data` identity plus a recursive content hash. It catches in-place edits of nodes, settings and links (tested), registry changes, and migrations (keyed on the raw data). Nested subgraph and loop graphs are compiled and validated on their own when they run (tested). In-place edits of a Resource inside the data are not seen, but the runs pick up the edited object, because settings receive the same object.
- **Run settings are fresh per run.** Overrides and bindings write Dictionary entries into a fresh copy. The order signature covers `disabled`, `inspect_enabled`, `debug_enabled` and `variable_name`. The execution order depends on nothing else that settings can change.
- **Output cache key.** The key covers:
  - settings after overrides and bindings (live when bound, precomputed otherwise);
  - graph seed;
  - the preview flag;
  - per-bulk input fingerprints (content hash plus size, stream count and attribute count);
  - virtual variable dependencies.

  No cacheable template reads `ctx.runtime_params`, `variables`, `owner`, `bounds`, `eval_id` or `graph`. I checked by grep; the WP5 bounds nodes are non-cacheable. `Data.duplicate()` copies everything `content_hash` covers, so hits are complete. Hits and stored entries are copies, and errors replay in order (also in threaded mode).
- **Threaded mode.**
  - Pool tasks and main-thread elements never overlap, and the group wait is always reached, because GDScript has no exceptions.
  - Nested threaded evaluations start only from main-thread elements, so there is no nested waiting inside pool tasks.
  - `node_filter` and preseeded elements behave as in sequential mode.
  - The cycle fallback is sequential.
  - Error order is deterministic (tested with nested loops and the cache).
- **`node_filter` and `preseeded`.** A filtered element produces nothing, and its consumers see a missing input, as in every mode. Preseeded bulk arrays are copied and the Data shared; WP9 shows that no stock node mutates its input.
- **Lifecycle.**
  - There are no RefCounted cycles: the element holds its widget as a plain Object reference, and the widget owns the element.
  - The compiled graph holds its graph weakly and holds no elements.
  - The ObjectDB stays flat in every mode.
  - Elements of a freed component are released.
- **Editor path.** The dock and the runtime agree on:
  - partial re-evaluation through variables, reroutes and disabled nodes (tested);
  - the golden set (existing harness);
  - variable renames, which re-dirty every variable node through `refreshVariableNodes`.

## Limits

- Headless only. I did not exercise:
  - the real `EditorUndoRedoManager`; undo and redo were simulated through `load_graph_state()`, which is exactly what the recorded undo actions call;
  - mouse interaction;
  - the inspector (`addNode()` itself calls `EditorInterface.get_inspector`, so the add test goes through `addNodeFromTemplate`);
  - the 3D debug draw.
- The Logger thread-safety hazard cannot be reproduced deterministically. Fix #7 is backed by a source scan, not by a crash reproduction.
- The scene-fingerprint fixes (#3, #4) are checked through `onEditorSceneChanged()` and `computeSceneFingerprint`, not through real editor scene edits.
