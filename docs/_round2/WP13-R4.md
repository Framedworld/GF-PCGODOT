# WP13-R4: adversarial review of spawners and generated-content ownership

Reviewer R4. Area: `spawn/*.gd` (FlowMeshSpawnEntry, FlowSpawnUtil, FlowInstancedCollision3D, FlowSpawnPool, FlowSplineBend); the nodes `spawn_meshes`, `spawn_scenes`, `spawn_nodes`, `spawn_spline_mesh`, `apply_on_actor` and `create_target_node`; and the ownership and cleanup code in `flow_node.gd` and `node.gd`.

Method: I read the area end to end and wrote a list of failure hypotheses. For each one I wrote a failing, headless-safe test first. If the test failed, I made the smallest fix and committed it with its test. All new suites are in `demo/tests/review_r4/` (13 suites, 55 cases).

## Confirmed bugs, fixed

| # | Commit | Bug | Test |
|---|---|---|---|
| 1 | `d9d6ebf` | **Name collisions.** When a spawned node's name was already taken, Godot's `add_child()` named it `@Class@N` from a process-global counter, without checking the siblings. The name could be taken by a user node, by another component's content in a shared parent, or by a second spawner of the same graph (the dungeon demo produced 1699 such names per generation). Unnamed MultiMeshInstance3Ds always went through this path. These names are saved with the scene, and the counter restarts in each session, so a later auto-name can equal a saved sibling's name. The parent then holds two children with the same name, `get_node(name)` returns the wrong one, and the name index loses an entry. ### Fix notes

1. **Names** (`FlowSpawnUtil.add_spawned_child`, `set_spawned_name`, `unique_child_name`).
   - **Named nodes.** A taken name becomes the first free `<name>_<k>`, with k ≥ 2. This costs one lookup per candidate. Godot's readable path counts the trailing number up through every taken name, which is quadratic when two spawners share a parent: it nearly doubled the dungeon's second generation (568 to 1063 ms), so it is not used.
   - **Unnamed MultiMeshInstance3Ds** keep the auto-name. The exception is a sibling holding a saved auto-name past the current counter, which is detected by probing the counter. In that case they get a readable name.
   - **Create Spline** sets its name before a readable `add_child`. Before, it renamed the node after a transient auto-name. The resulting names are unchanged (`Spline`, `Spline2`).
   - **Pooled nodes are renamed through the same check.**
   - **Reproduction.** In 4.6.stable, saved children named `@Node3D@N` (N just past the counter) plus a sibling that takes the canonical name are enough: a spawned node then lands on an existing name. The fast path never checks.
2. **Copies.** `FlowNodeBase.isStaleFlowComponent(id, content, component_root)` treats content inside the asking component's subtree as stale in two cases:
   - the id names a live object that is not a Node3D (a reused id);
   - the id names a live component that did not spawn that node. The new `FlowGraphNode3D.owns_flow_content(node)` answers this: the node was recorded by `note_spawned_content`, or the component has untracked content.

   `isOwnFlowContent(meta, ctx, content)` passes the content through. It is used by `removeOwnFlowContent`, `FlowSpawnPool.collect`, `create_target_node` and `cleanup()`. Content that another live component recorded is still left alone.
3. **Spawn session.** `FlowNodeBase.SPAWN_SESSION_META` holds one Dictionary per top-level evaluation.
   - **Creation.** The executor creates it and shares it with nested subgraph and loop evaluations (one line in `executor/flow_executor.gd`). The editor starts a new one per evaluation (one line in `flow_editor.gd`).
   - **Use.** `tagFlowContent` records every tagged node in it. `removeOwnFlowContent` and `FlowSpawnPool.collect` skip the nodes it holds.
   - **Elements run by hand** have no session and behave as before.
4. **Stale parents.** `FlowGraphNode3D.recorded_content_parents(node_name)` and `FlowNodeBase.previousContentParents(ctx)` feed the parents of a spawner's recorded content into its clear and pool parents. The matching rules are unchanged.

## Output and baseline changes

- **Golden suite:** unchanged.
- **Seed-zero suite:** three entries changed in commit `d9d6ebf` (names only):
  - `res://demos/demo_dungeon.tscn`
  - `res://graphs/graph_dungeon_stress_test.tres`
  - `res://graphs/subgraph_dungeon_upper_level.tres`

  In each, only the generated-scene part of `result` changed. The per-node `nodes` hashes and the output hashes did not. The cause: every spawn_scenes node after the first in the dungeon graph spawns `Scene_0000…` under the same owner. Their nodes used to be `@Node3D@N` auto-names, which the hasher folds to `@Node3D`; they are now `Scene_NNNN_2`, `_3`, and so on.

  Proof that only names changed:
  1. I replaced the hasher's name normalisation with "class only", on a local edit that was not committed.
  2. I wrote a baseline with the old code and compared the new code against it: every graph and demo scene matched.
  3. I restored the real hasher and regenerated the baseline with `FLOW_WRITE_SEED0_BASELINE=1`. The diff touches exactly those three entries.

  This is the fix itself: the old names are the auto-names that collide in later sessions.
- **Intended output changes.** These are not covered by any baseline:
  - spawners fed several bulks, or inside a loop or a repeated subgraph, now keep everything (fix 3);
  - after a spawn-parent or container edit, the stale content and container are removed (fixes 11 and 12);
  - names change only where they used to collide (fix 1).

  Suggested DEPRECATIONS rows:

| Change | Before | After |
|---|---|---|
| Spawner fed several bulks, or in a loop or a repeated subgraph | Only the last bulk or iteration stayed | Every bulk and iteration stays; earlier generations are replaced |
| Spawned node whose canonical name is taken | `@Node3D@N` auto-name | `<name>_<k>` (k ≥ 2) |
| Spawn parent or target container changed between generations | Previous content or container stayed until `cleanup()` | Replaced on the next generation |
| `%Unique` override missing in the spawned instance | Wrote into the level's unique node | Reported as an unresolved path |

## Suspected, not confirmed or not fixed

- **`FlowSpawnUtil.clear_collision` on reuse frees every StaticBody3D child of a pooled MMI or segment**, including one a user added by hand. I did not fix it because generated content is not meant to be hand-edited.
- **Pool keys of unsaved resources (`#<instance id>`) can match across sessions.** Instance ids are deterministic per process, so an id saved in `flow_pool_key` can name a different resource in a new session. For meshes this is harmless, because the mesh and material are reassigned on reuse. For an embedded (unsaved) PackedScene, a node instanced from another scene could be reused. Not reproduced.
- **Stale component ids from different components.** After a reload, every component's content carries a stale id, and a spawner treats any stale content with its own node name as its own. With two components sharing a parent and using the same spawner node names, the first component to regenerate frees the other's saved content. The other then respawns it on its own generate, so it only matters if only one of them regenerates.
- **`cleanup()` after a scene reload does not find content spawned outside the component's subtree.** The records are per session, and stale ids are only trusted inside the subtree. The next `generate()` does clear it, through the spawner's own clear step.
- **`segments_for_spline` uses `Curve3D.get_closest_offset` per control point.** A curve that passes through one of its own earlier control points can mis-segment. Two exactly coincident consecutive points make Godot's bake fail (`looking_at` errors) and gave a single segment. This is an engine bake issue, not reproduced as a spawner bug otherwise.
- **Weighted entry selection with a NaN weight** (code-set only; the inspector cannot produce it) collapses every pick onto the last positive entry. `maxf(0, NaN)` returns NaN in Godot.
- **`coerce_value` of a NaN float to an int property** gives INT64_MIN, which is Godot's `int(NaN)`.

## Checked and judged fine

- **FlowInstancedCollision3D:**
  - rebuilds clear every shape owner;
  - the shape-owner count equals the instance count after `setup()`, after a pack and instantiate round trip, and after `duplicate()`;
  - zero and negative instance scale produce no physics errors with Godot Physics, and rays still hit.
- **MultiMesh reuse:**
  - the entries path resets the colour and custom-data flags at count 0 before resizing;
  - the legacy and entries pool keys cannot collide;
  - mesh swaps happen at count 0.
- **Pooling:**
  - it is per parent, and pooling across parents never moves nodes;
  - shrink and grow work;
  - two spawner nodes in one graph pool separately, by node name;
  - `transient_output` toggling clears the owner on reuse.
- **Mesh entries:**
  - null entries, entries without a mesh, all-zero or negative weights, out-of-range and NaN index selectors (clamped, deterministic), and unmatched names (reported) are handled.
- **Spawn parents:**
  - a freed parent or a non-Node3D value falls back with an error;
  - relative and absolute NodePaths both resolve.
- **Async generation:**
  - `cleanup()` during `generate_async()` leaves nothing;
  - `generate()` or `regenerate()` during an async run leaves exactly one set.
- **Saving:**
  - content under a Transient container or an unowned parent is never packed (see `r4_transient_container_save_test.gd`);
  - content under a child of an instanced sub-scene keeps the scene owner.
- **Spline bend:**
  - non-indexed surfaces are supported;
  - surfaces without normals or tangents, and surfaces with `ARRAY_CUSTOM0` data, bend without errors;
  - the cache is bounded at 256 entries.

## Limits

- Headless only. The dummy RenderingServer stores no MultiMesh instance data, so visual results (visible instances, colours) were not checked. The pool reset is checked on the properties.
- **Timing.** These numbers are from single runs in a shared container. Second generation of `graph_dungeon_stress_test` (1817 scene instances):

  | | Second generation |
  |---|---|
  | Before | about 570 ms |
  | After | about 650–690 ms |

  The extra cost is the name-uniqueness lookup per spawned node and the record walk per spawner.
- **The spawn session covers evaluations that go through FlowExecutor or the editor.** A custom caller that builds its own context and runs elements directly keeps the old replace-every-run behaviour.
- **Changes outside the area:**
  - one line each in `executor/flow_executor.gd` and `flow_editor.gd` (fix 3);
  - `create_spline.gd` (fix 1, same collision class);
  - `tests/runtime/seed_zero_baseline.json` (three entries, explained above).
